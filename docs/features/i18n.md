# 🌐 i18n — Documentación

## Alcance actual

Se instaló `react-i18next` + `i18next` como motor real de traducción, pero
**el alcance de la migración es acotado a propósito**:

- ✅ El modal de **Ajustes** (`SettingsModal`) está completamente traducido.
- ✅ Los diccionarios de labels que existían como archivos separados
  (`ROLE_LABELS`, `STATUS_LABELS`, `SHOP_SALES_RANGE_LABELS`,
  `PRESENTATION_CATEGORY_LABELS`, `SALE_TYPE_LABELS`, `MODEL_TYPE_LABELS`,
  `MODEL_UNIT_LABELS`, `PAYMENT_METHOD_LABELS`) y el mapa de errores de auth
  (`authErrorMessages.ts`) se migraron a `src/i18n/locales/*` — **esos
  archivos `*Labels.ts` ya no existen**.
- ❌ El resto de la app (Ventas, Productos, Boletas, Vendedores,
  Proveedores, formularios, tablas, etc.) sigue con texto hardcodeado en
  español. Cambiar el idioma desde Ajustes **no traduce esas pantallas**.

Fue una decisión de scope explícita (ver conversación del feature): migrar
toda la app de una es un trabajo mucho más grande, tocando prácticamente
todos los módulos.

## Estructura

```
src/i18n/
├── i18n.ts              # init de i18next + LANGUAGE_STORAGE_KEY
└── locales/
    ├── es.ts             # default (fallbackLng)
    └── en.ts
```

- `i18n.ts` se importa como efecto lateral una sola vez, en `src/main.tsx`
  (`import "./i18n/i18n"`) — y también en `src/modules/shared/test/utils/setupTests.tsx`,
  así los tests tienen `t()` funcionando sin tener que envolver cada test
  en un provider de i18next.
- El idioma persiste en `localStorage` bajo la key `"appLanguage"`
  (`LANGUAGE_STORAGE_KEY`, exportada desde `i18n.ts` — **no** desde
  `config/constants.ts`, para evitar un ciclo de imports con los
  consumidores no-React que usan `i18n.t()` directo, ver abajo).

## Dos formas de usar `t()`

**Dentro de un componente o hook** (reactivo — el texto se actualiza solo
cuando cambia el idioma):

```tsx
import { useTranslation } from "react-i18next";

const { t } = useTranslation();
<Typography>{t("settings.appearance.mode.heading")}</Typography>
```

**Fuera de React** (registries estáticos, `valueGetter` de columnas de
`DataGrid`, helpers puros) — se importa el singleton configurado y se
llama `.t()` directo. No es reactivo a un cambio de idioma en vivo (no hay
`useTranslation` suscribiendo un re-render), pero como estas funciones se
evalúan de nuevo en cada render/uso, no queda texto "pegado" del idioma
viejo más allá de ese caso puntual:

```ts
import i18n from "@i18n/i18n"; // alias @i18n → src/i18n

getOptionLabel: (v) => i18n.t(`roles.${v}`),
```

Ejemplos reales de este segundo patrón: `getRoleLabel.ts`,
`SellerFieldRegistry.ts`, `PresentationFieldRegistry.ts`,
`ProductExhibitorColumns.tsx`, `formatDetail.ts`, `SummaryItems.tsx`.

## Namespaces del diccionario

| Key raíz | Para qué |
|---|---|
| `settings.*` | Todo el modal de Ajustes |
| `roles.*` | `AuthRoleEnum` (admin/seller) |
| `sellerStatus.*` | `SellerStatus` (online/offline) |
| `shopSalesRange.*` | `ShopSalesRange` (rango del gráfico de /shop) |
| `presentationCategory.*` | `PresentationCategory` (33 categorías) |
| `saleType.*` | `SaleType` (unit/weight) |
| `modelType.*` | `ModelType` (envase/formato) |
| `modelUnit.*` | `ModelUnit` (unidad de medida) |
| `paymentMethod.*` | `PaymentMethod` |
| `authErrors.*` | Mensajes crudos del backend (keys en inglés, tal cual los devuelve el server) traducidos — ver `translateAuthError` en `store/shared/authErrorMessages.ts` |

Las keys de `presentationCategory`/`modelType`/`modelUnit`/`shopSalesRange`
usan el **valor string del enum** (ej. `deli_and_cheese`, no `DeliAndCheese`),
para poder hacer `t(`presentationCategory.${value}`)` sin una tabla de
mapeo intermedia.

`authErrors` es distinto: sus keys son el mensaje crudo del backend en
minúsculas (pueden tener puntos, ej.
`"password is incorrect. make sure caps lock is off and try again."`).
Por eso `translateAuthError` no le pasa la key completa a `t()` (i18next
trata `.` como separador de anidamiento por default) — en cambio pide el
objeto completo con `t("authErrors", { returnObjects: true })` y hace el
lookup con acceso plano de JS.

## Riesgo conocido: opciones "congeladas" fuera de un render reactivo

Algunos `Record<Enum, string>` estáticos (ej. `PAYMENT_METHOD_OPTIONS` en
`config/constants.ts`) se evaluaban **una sola vez al importar el módulo**.
Si se les hubiera puesto `i18n.t()` ahí directo, el label habría quedado
congelado en el idioma que estuviera activo en ese primer import, sin
reaccionar nunca a un cambio de idioma posterior. Se resolvió sacando esas
opciones del módulo estático y computándolas en el render del componente
que las consume (ver `CartPaymentMethod.tsx`, que ahora mapea
`PAYMENT_METHOD_VALUES` con `t()` en vez de importar un
`PAYMENT_METHOD_OPTIONS` precalculado).

## Cómo agregar una traducción nueva

1. Agregar la key en **ambos** `src/i18n/locales/es.ts` y `en.ts`.
2. Consumirla con `useTranslation()` si estás en un componente/hook, o con
   `i18n.t()` (`import i18n from "@i18n/i18n"`) si estás en un archivo
   fuera de React.
3. Si es un diccionario `Record<Enum, string>` nuevo, usá el **valor**
   del enum como key (no el nombre del identificador de TS).

## Tests

Ver `src/hooks/ui/test/useLanguageOption.test.ts` para el patrón de test
con i18next real (no mockeado): cambiar idioma con el hook, esperar con
`waitFor` a que el componente reaccione, y resetear con
`i18n.changeLanguage(LanguageEnum.Spanish)` en `afterEach` para no filtrar
estado entre tests.
